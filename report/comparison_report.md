**Analysis Questions:**

1. **Why does QoS 0 lose messages while QoS 1 and 2 do not?** *(2–3 sentences)*

   > QoS 0 operates on a "fire-and-forget" model with no acknowledgments. If the network drops a packet, neither the sender nor the receiver knows it was lost, and no retransmission occurs. QoS 1 and 2, however, require acknowledgment packets (PUBACK, or a 4-step handshake) and will automatically retransmit the payload if the acknowledgment is not received within a timeout period.

2. **QoS 1 may show duplicates. Under what circumstances does this happen, and is it a problem for sensor telemetry?** *(2–3 sentences)*

   > Duplicates happen in QoS 1 when the original PUBLISH message successfully reaches the broker, but the broker's PUBACK acknowledgment is lost on the way back. The sender assumes the message was dropped and resends it, resulting in the broker processing it twice. For absolute sensor telemetry (e.g., "temperature is 25°C"), this is usually harmless because processing the same state twice doesn't change the outcome, but it would be catastrophic for relative commands (e.g., "increase speed by 5 RPM").

3. **QoS 2 has higher latency than QoS 1. What causes this, and when is the trade-off worth it?** *(2–3 sentences)*

   > The higher latency in QoS 2 is caused by its 4-step handshake (PUBLISH, PUBREC, PUBREL, PUBCOMP), which requires double the network round-trips compared to QoS 1's 2-step handshake. This trade-off is absolutely worth it for safety-critical actuator commands (like turning on a heavy machine) or financial transactions where executing a duplicate command could cause physical damage or data corruption.

## 5.3 Protocol Selection Recommendation

### Data Path Recommendations

| Data Path | Recommended Protocol | Justification |
|-----------|---------------------|---------------|
| Sensor → Cloud (high frequency, <100 ms latency) | MQTT QoS 0 (or CoAP NON) | Lowest network overhead and fastest transmission speed for highly frequent, idempotent data. |
| Actuator commands (safety-critical, exactly-once) | MQTT QoS 2 | Guarantees exactly-once delivery; prevents dangerous duplicate commands from executing twice. |
| Backend service-to-service routing | AMQP | Advanced routing (topic/direct/fanout exchanges) and robust message queueing capabilities. |
| OTA firmware delivery to constrained MCU (Class 2) | CoAP CON | Built-in Block-wise transfer handles large file fragmentation natively over UDP without heavy TCP overhead. |

### Detailed Justification

> Based on the implementation, packet captures, and testing results from Tasks 1 through 4, the recommendations above are heavily driven by the specific operational constraints of a manufacturing environment.
>
> For **Sensor to Cloud telemetry**, the sheer volume of data generated by factory production lines requires a protocol with minimal overhead. As seen in the packet analysis (Task 4), MQTT QoS 0 and CoAP NON provide extremely lightweight headers. While the QoS test (Section 5.1) proved that QoS 0 drops roughly 50% of messages during network congestion, high-frequency sensor data is idempotent and rapidly superseded by the next reading (e.g., a temperature reading at 10.0s is irrelevant if we receive the 10.1s reading). Therefore, trading reliability for the observed ~2.5ms ultra-low latency is the correct engineering decision.
>
> Conversely, for **Actuator commands**, reliability is paramount. Sending an "ON" command to an industrial fan or robotic arm cannot be lost, nor can it be executed twice if it is a toggle command. MQTT QoS 2 utilizes a 4-step handshake to guarantee exactly-once delivery. While our tests showed QoS 2 latency is nearly double that of QoS 1 (~14.3ms vs ~8.1ms), actuator commands are infrequent, making the latency hit acceptable in exchange for absolute systemic safety.
>
> For **Backend routing**, AMQP is the undisputed choice. While we skipped the implementation for this module, AMQP's architecture separates exchanges and queues, allowing for complex routing topologies (e.g., fanning out vibration data to both a real-time alerting service and a cold-storage database). Neither MQTT nor CoAP provide this level of backend flexibility natively.
>
> Finally, **Over-the-Air (OTA) firmware delivery** requires transmitting megabytes of data to constrained microcontrollers (MCUs). The CoAP protocol natively supports Block-wise transfers (Block2). As demonstrated in Task 2's manifest fetch, CoAP automatically slices a large payload into manageable UDP datagrams and reassembles them. Doing this over MQTT requires manual application-level fragmentation logic, and doing it over HTTP requires a heavy TCP stack which Class 2 MCUs often cannot support.

## 5.4 Reflection

### Technical Challenge

> *Describe one technical challenge you encountered in the implementation and how you resolved it.*
> One major challenge was the asynchronous event loop management in Python, specifically when integrating `aiocoap` with the `pytest-asyncio` testing framework. The provided automated test script (`test_server.py`) initially crashed with an `attached to a different loop` RuntimeError. I diagnosed this as a version conflict where `pytest-asyncio` was spinning up function-scoped event loops, conflicting with the module-scoped `coap_server` fixture. Since the assignment prohibited modifying the test file, I successfully resolved the framework bug by modifying `pytest.ini` to enforce a module-level loop scope (`asyncio_default_fixture_loop_scope = module` and `asyncio_default_test_loop_scope = module`). Additionally, I resolved a MacOS-specific IPv6 'any-address' binding restriction by explicitly forcing the CoAP server to bind to `127.0.0.1:5683`.

### Most Surprising Protocol Difference

> *Describe the most surprising difference you observed between the protocols during the packet capture task.*
> The most surprising difference was how aggressively CoAP minimizes its packet overhead compared to MQTT. The MQTT CONNECT packet required 43 bytes, explicitly spelling out "MQTT" in ASCII along with multiple flag bytes and client IDs. By contrast, a CoAP CON GET request squeezed the Version, Type, Token Length, and Code into a single byte (`0x44`), relying entirely on bitwise flags. It highlighted exactly why CoAP is preferred for heavily constrained NB-IoT or LoRaWAN networks where every byte costs battery life.

### Most Complex Protocol to Implement

> *Which protocol was the most complex to implement correctly, and what specifically made it harder?*
> MQTT was significantly more complex to implement correctly due to the application-level state tracking required for QoS 1 and 2. With MQTT, I had to manually manage packet identifiers, track unacknowledged messages, and implement persistent queuing logic (the LWT and session states). CoAP felt much simpler from a developer standpoint because the `aiocoap` library seamlessly abstracted the complexity of CON/NON retransmissions and Block2 payload fragmentation entirely away from the application code.
